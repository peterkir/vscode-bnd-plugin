When Eclipse Bndtools and VS Code have the **same bnd workspace directory** open, both write the same compiler output (`bin`, `bin_test`) and bundle output (`generated`). The extension detects this situation and can give VS Code its own output directories, so neither IDE overwrites the other's results.

Background and the remaining conflicts are described in [Sharing a workspace directory with Eclipse Bndtools]({{ site.repository_url }}/blob/main/docs/shared-workspace-conflicts.md) (design "A. Twin").

## Detection

For every workspace folder that is a bnd workspace root (it contains `cnf/build.bnd`) the extension reads `.metadata/.lock_info`. Eclipse writes this file when it opens a workspace and records host name and process id. An Eclipse instance is reported when that process is running on this machine. The check runs when the extension activates, when the file or the workspace folders change, and every 30 seconds.

Limits:

- The Eclipse workspace location must be the bnd workspace root, so that `.metadata` lies next to `cnf`. An Eclipse workspace elsewhere that only imports the bnd projects is not detected.
- The Eclipse version must write `.lock_info`. Older versions do not.
- Eclipse does not delete `.lock_info` on exit. If the operating system reuses the recorded process id for another process, Eclipse is reported although it is not running.

## Status bar item and notification

While an Eclipse instance is detected, an **Eclipse** item appears next to **bnd LS**.

- **Warning background:** VS Code and Eclipse write the same build output.
- **Link icon, no background:** separate output directories are configured.

Click it, or run **bnd: Eclipse Parallel Use...**, to configure or remove the separate output, enable or disable the language server, open the documentation, or open the output channel.

The first time in a session that Eclipse is detected on a workspace without separate output, a warning offers **Use Separate Output**, **Details**, and **Don't Show Again**. The last choice is stored per workspace.

Set `bnd.eclipse.detect` to `false` to turn off the detection, the status bar item, and the notification.

## Configure separate output

Run **bnd: Configure Parallel Use with Eclipse...**. If several workspaces are open you pick one. After you confirm, the command

1. creates `cnf/ext/vscode-outputs.bnd` (below),
2. with Language Support for Java installed, sets `java.project.resourceFilters` to `[]` in the workspace settings so the Java language server stops adding a resource filter to Eclipse `.project` files and removes the one it added, and
3. removes the classpath container `org.bndtools.jdtls.BND_CONTAINER` from the `.classpath` of Eclipse Bndtools projects. Extension versions before 0.28.0 wrote that entry; Eclipse cannot resolve it.

The command works whether or not Eclipse is currently detected.

```properties
# Generated by the bnd VS Code extension (bnd: Configure Parallel Use with Eclipse).
# Gives VS Code its own compiler and bundle output next to the Eclipse output.
# The bnd language server and the Java project import report the driver 'vscode';
# Eclipse Bndtools, the bnd CLI and Gradle keep bin, bin_test and generated.
vscode.outputs: ${if;${driver;vscode};.vscode}
bin: bin${vscode.outputs}
testbin: bin_test${vscode.outputs}
target-dir: generated${vscode.outputs}
```

| Tool | `bin` | `testbin` | `target-dir` |
|---|---|---|---|
| VS Code (bnd language server, Java project import) | `bin.vscode` | `bin_test.vscode` | `generated.vscode` |
| Eclipse Bndtools, bnd CLI, Gradle | `bin` | `bin_test` | `generated` |

## Things to know

- Eclipse builds are unchanged: the macro is empty for every driver except `vscode`. Apart from step 3 the extension writes no Eclipse file.
- Directories are routed by the bnd driver name. The bundled server passes the driver `vscode`; a server from another source that ignores it keeps `bin`, `bin_test`, and `generated`. Check it with **bnd: Evaluate Macro (LSP)** and `${driver}`.
- Add `bin.vscode/`, `bin_test.vscode/`, and `generated.vscode/` to your `.gitignore`.
- The language server and the Java import pick up the new file without a restart. If Java output still goes to `bin`, run **Java: Clean Java Language Server Workspace** once.
- Files in `cnf/ext` are read before `cnf/build.bnd`. If `bin`, `testbin`, or `target-dir` is already defined in `cnf/build.bnd` or another `cnf/ext/*.bnd` file, the command reports the file and line and writes nothing.
- A project that defines these keys in its own `bnd.bnd` keeps its directories in both IDEs. The command lists such projects in the **bnd Language Server** output channel.
- Launch storage is separated only when a launch's storage directory follows the target directory (for example `-runstorage: ${target-dir}/fw`) or uses `${driver}`. The command lists `.bndrun` files whose `-runstorage` or `launch.storage.dir` does not, because those launches still share runtime storage.
- Repository indexes and `cnf/cache` stay shared. The bundled language server takes part in cross-process locks for index, project output, and launch storage; Eclipse does so once its Bndtools version contains them.
- Running the command on a workspace that already has the file offers to remove it. The `*.vscode` directories are not deleted and `java.project.resourceFilters` is not changed back.

## Imported Eclipse projects

The native Java import never changes `.project`, `.classpath`, or `.settings` of a project that Eclipse Bndtools manages. It keeps that project's classpath in memory, applies it again when Eclipse rewrites `.classpath`, and resolves the Bndtools classpath container `aQute.bnd.classpath.container`. Compiler settings come from the Eclipse project.
